# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Zenith is a macOS 26+ menu-bar utility (Swift 6.2, SwiftUI + AppKit, SwiftPM only — no Xcode project): clipboard history, screen capture/annotation, Vision OCR, a notch "Dynamic Island" (Now Playing, charging HUD, drop shelf), disk cleaner, and a DoH/anti-DPI local proxy. `README.md` is the accurate feature reference.

## Commands

```bash
swift build                          # debug build
swift run Zenith                     # run the menu-bar app (also: --smoke-test, --version, --help)
swift test                           # whole suite (Swift Testing: @Suite/@Test/#expect)
swift test --filter NowPlayingAndBatteryHUDTests   # one suite; a test function name also works
./scripts/test_each_suite.sh         # every suite in its own process (what CI runs); ONLY_SUITES="A B" limits it
swift run Zenith --render-screenshots DIR   # PNGs of the island, Command Hub and clipboard with made-up data (website/assets/shots)
./scripts/bundle_app.sh              # release build -> Zenith.app, signed by scripts/sign_app.sh (local identity if present, else ad hoc)
./scripts/setup_signing.sh           # once per Mac: self-signed "Zenith Local Signing" identity in the login keychain
./scripts/create_dmg.sh              # release DMG
./scripts/check_localization.sh      # strings the code uses that Localization/vi.lproj does not translate (~1.5 min)
```

- No linter/formatter is configured. `.github/workflows/tests.yml` builds the app and runs `scripts/test_each_suite.sh` on `macos-26` (its first runs on GitHub exposed Swift 6.1 differences and suites that die without a window server; see the PR); `deploy-pages.yml` publishes `website/`. A single `swift test` over all suites can stall (blocking tests starve the thread pool), which is why the script runs one suite per process. `VisionChallenger2EmpiricalTests` (8K OCR memory ceiling) fails on some machines (it does on the author's Mac, not on the CI runner); the script's `EXPECTED_FAILING_SUITES` can list such a suite. CI skips four suites that create a menu-bar item or window (`SKIPPED_SUITES` in `tests.yml`): the runner's test process has no window-server connection and aborts with `CGSConnectionByID … is_initialized`. They only run on a Mac with a desktop session.
- `Package.swift` adds `-load-plugin-library …/CommandLineTools/…/libTestingMacros.dylib` to the test target only when the Command Line Tools are the active developer directory (`DEVELOPER_DIR` / `/var/db/xcode_select_link`) and the plugin exists; with full Xcode selected the toolchain supplies it. A cold `swift test --filter` takes ~45 s, nearly all of it compiling.
- `Info.plist` is generated by a heredoc inside `scripts/bundle_app.sh`; plist keys (e.g. `NSAppleEventsUsageDescription`) are edited there. `Zenith.app` and `*.dmg` in the repo root are gitignored build outputs.
- **The deployment target is macOS 26** (raised from 13 to 15, then to 26 so the redesign can use Liquid Glass (`glassEffect`) without a second code path; `platforms` in `Package.swift`, which needs `swift-tools-version: 6.2` for `.v26`, and `LSMinimumSystemVersion` in the `bundle_app.sh` heredoc; keep the two equal). Nothing in the code checks the macOS version at run time. Screen capture is ScreenCaptureKit only (`CGDisplayCreateImage` is obsolete from macOS 15 and no longer compiles): `NativeScreenCaptureBackend` captures with `SCScreenshotManager` and leaves out the windows in `ScreenCaptureExclusions`, where `CaptureOverlayController` registers its dimmed selection panels while they show (ScreenCaptureKit answers after the overlay is up, so without that the loupe would sample a darkened screen). The stores are still `ObservableObject`, **not** `@Observable` (allowed now, not migrated yet: every mutation must call `objectWillChange.send()`; `SettingsStoreTests` checks that each setting does). SF Symbol names are strings, so the compiler cannot flag one that macOS 26 lacks: it draws nothing and logs "No symbol named …". Give a symbol newer than macOS 26 a fallback with `SymbolName.available` (Core). `create_dmg.sh` makes an HFS+ image on purpose (it mounts everywhere). CI runs on `macos-26`, the oldest supported macOS.
- The version is declared once, in `Sources/ZenithCore/Models/ZenithVersion.swift`; `--version`, `bundle_app.sh` (Info.plist) and `create_dmg.sh` read it from there. Only the DMG file name in `README.md` and `VERSION` in `website/js/core.js` are typed by hand.
- **Tests must not change the machine running them.** Services that touch the OS take an injected seam (`SystemCommandRunner` for `networksetup`/`lipo`/`codesign`/`defaults`/`lsregister`, a pasteboard, an event poster), and tests use `RecordingCommandRunner` / `FakeNetworkSetup` / `NSPasteboard.withUniqueName()`. `ClipboardStore(capacity:)` already gets a private pasteboard. The two suites that really do change things are opt-in: `ZENITH_E2E_SYSTEM=1` (`PrivacyShieldE2ETest` flips the real system proxy; `HKC-E2E` registers real global hot keys for a moment) and `ZENITH_E2E_NETWORK=1` (`PrivacyShieldLiveTest`, uses the internet). `ZENITH_E2E_SIGNING=1` (`UpdateSignatureE2ETests`) creates a throwaway keychain file (never added to the search list, deleted afterwards) to sign fake apps.
- `--filter` matches test *function* and *suite* names, not the `"LP-07: …"` display names; a filter that matches nothing still prints a passing run, so check the test count.
- Test bodies are `async`, so blocking socket calls inside them starve the cooperative thread pool that the code under test also needs. Run blocking I/O with the `offPool { }` helper in `LocalProxyServerBehaviorTests.swift`.

- The site in `website/` is plain HTML/CSS/JS with no third-party requests and is deployed by `deploy-pages.yml` on every push to `main`. It is a pretend Mac desktop on which every feature can be tried with made-up data (ES modules in `website/js/`, no build step; `core.js` has windows, menus, dialogs, shortcuts and notices, and `VERSION`, which must equal `ZenithVersion.current`). Preview it with a static server (`python3 -m http.server 8765 -d website`, also in `.claude/launch.json`). Dialogs and panels (`.scrim`, z-index 100) must stay above the island (40). After changing the site, raise every `v=` in the import-map block of `website/index.html` (it versions each module), or browsers keep running old modules mixed with new ones. Its OCR reads the page's own words and its captures repaint the page into a canvas; the QR code in Sample.png is a real one (`js/qr.js`). Its screenshots come from `--render-screenshots`, which draws the real views in an off-screen `NSWindow` (`ImageRenderer` cannot draw text fields or scroll views). `ZenithCommandHubState.snapshotProvider` exists so those images show made-up processes: the hub refreshes itself from the real machine when it appears, so never publish a render that skipped it.

## Architecture

Two targets plus tests:

- **`ZenithCore`** (library): all logic, models, protocols and mocks. It is *not* AppKit-free: `MenuBarController`, `ZenithIslandState` (SwiftUI `Color`), `NowPlayingService` etc. live here so they can be unit-tested.
- **`ZenithApp`** (executable `Zenith`): `main.swift` sets `.accessory` activation policy; `AppDelegate` wires menu-bar callbacks and Carbon global hotkeys (`HotKeyManager`, no Accessibility permission needed) to `*Controller.shared` window controllers, which host SwiftUI views. `MenuBarController`, `PanelPositioner` and `KeyboardNavigationEngine` here are `typealias` re-exports of the ZenithCore type — **edit the ZenithCore file**. `SettingsWindowController` is also a re-export, plus an extension that injects the SwiftUI `ZenithPreferencesView` (Core can't reference App views).
- The Command Hub popover closes when Zenith stops being the active app (a transient popover does not, on ⌘Tab, and then kept sampling processes every 2.5 s), and both it and the Settings window drop their SwiftUI content 30 s after closing (`scheduleRelease`, `SettingsWindowController.contentReleaseDelay`); Settings then reopens on its default tab.
- **Command Hub layout** (Control Center style, `ZenithCommandHubView`, 392 pt wide, 14 pt padding, 10 pt between rows): a search capsule (no shortcut hint: the hub has no shortcut for the field, do not invent one), two toggle tiles (`HubPrivacyShieldTile`, `HubKeepAwakeTile`: filled with the feature colour and white text while on; a click does what the old switch did, Keep Awake's clock menu and context menu hold its modes), a module of 60 pt ring gauges (CPU, Memory, Free Space, Battery when there is one) with the network line, the Running Apps module (real icon, memory, thin CPU bar, CPU %, quit button shown on hover or keyboard focus only, still after a confirmation; an app and its helpers are one row, `ProcessGrouping` (Core): the process list is read with `ps … comm=` without `-c`, which gives the full executable path, the outermost `.app` in it is the owner, CPU and memory are summed and the PID is the app's own process, which is the one asked to quit; the grouping runs in `parseProcessOutput` before the busiest are picked) and a footer (Listening Ports capsule `HubPortsButton`, round Settings and Quit). While searching, the matching actions come first and matching ports get their own module; Clean/Boost are two capsules under the tiles only when the island has no dock. The pieces are in `HubComponents.swift` (`HubSurface`, `hubModule()`, `hubCapsule()`, `HubRingGauge`, `HubToggleTile`, `HubAppRow`, `HubCircleButton`); thresholds, ring/bar fractions and the tile status lines are `HubStatus` / `HubGaugeLevel` (Core, `HubStatus.swift`, tested in `HubStatusTests`). Modules are semantic translucent fills with a 1 pt edge, **not** `glassEffect`: the popover behind is already Liquid Glass (glass on glass reads as mud) and the island page is black. Rows below the search field carry their own 10 pt top padding instead of stack spacing, because the ports list and the Homebrew capsule are usually empty and would leave a gap. Draw capsules as `RoundedRectangle(cornerRadius: 1000, style: .circular)`: `Capsule` with a stroke leaves stray edge marks in the off-screen renders. `--render-screenshots` draws the hub on a flat stand-in for the popover (radius 30), since the real glass is not there off screen.
- **`ZenithCoreTests`** covers ZenithCore only; `ZenithApp` has no tests, so put anything that needs a test in Core.

Patterns that span many files:

- **Protocol + mock seams**: `Protocols/*Protocol.swift` define the OS-facing services (pasteboard, screen capture, sound, hotkeys, permissions, launch-at-login). Matching `Mock*`/`Simulated*` implementations live in `Sources/ZenithCore/Mocks/` (in the library, not the test target) and make tests headless (no TCC prompts, no audio).
- **Singletons everywhere**: ~48 `static let shared` (`ClipboardStore`, `SettingsStore`, `ZenithIslandState`, every controller). Many are `@MainActor`. Stores also take injected dependencies in `init` for tests (e.g. `SettingsStore(userDefaults:)`).

### Dynamic Island pipeline

Producers write into `ZenithIslandState.shared` (`activeAlert`, `nowPlayingTrack`, `droppedItems`, hover/expand flags); `ZenithDynamicIslandView` renders it inside one **fixed-size `NSPanel`** (the island as it opens is **380** × 130 pt, plus `dockHeight` 66 with the dock: 196 pt tall in all. **It is never wider than 380 pt, pages included**: it is a black bar over the menu bar, and anything wider covers the status items beside the notch (on the author's 13" Mac, 1372 pt wide with the notch centred at 686, it spans 496 to 876 and clears them in normal use; 330 pt was tried in the redesign and was too cramped, 440 and a 640 × 294 Liquid-Glass pass covered them). Lay new content out for 380 pt, with 14 pt of side padding, so cards are 352 wide) owned by `ZenithIslandWindowController`. The panel never resizes — the SwiftUI view morphs inside it, so window bounds can't tell you which state is showing. Hover/drag hit-testing is done by global + local `NSEvent` mouse monitors in `handleMouseMoved`, which toggle `panel.ignoresMouseEvents` so clicks pass through everywhere outside the capsule. The global mouse and scroll monitors are not always installed: a global monitor has the window server send this process every event the user makes anywhere (4–10% of a core while the pointer moved), so `pollPointer` reads `NSEvent.mouseLocation` on a timer (`IslandPointerWatch`, Core: 0.1 s while the pointer moves, 0.5 s once it has rested 2 s) and installs them only while the pointer is within 80 pt of the panel or the island is taking mouse events; do not go back to an always-on global monitor. Geometry (notch vs. no-notch, per-state frames) is `ZenithIslandGeometry`. Hover does not open the island at once: `ZenithIslandState.onMouseEnter()` sets `isHoverEmphasized` (the view draws the closed island 8 pt wider per side and, under a notch, 5 pt taller; skipped with Reduce Motion) and opens after `hoverOpenDelay` (a setting in `IslandWidgetSettings`, 0.1–1 s, default 0.25 s) only if the pointer is still there; `open()` is the immediate path (a dragged file, a swipe, a click). A click on the closed island is caught by a local `leftMouseDown` monitor that only sees clicks delivered to the panel (which takes events only while the pointer is in `activeScreenRect`) and asks `ZenithIslandState.handleClick(pointerOnIsland:)`; the hosting view's `hitTest` still refuses everything while the island is closed. Tests that need an open island set `hoverOpenDelay = 0` or call `open()`; `open()` (and `openPage` from closed) first pins `activeTab` to the tab the island would show right now (`pinTabForOpening`), so a track or an agent arriving while it grows cannot change the card halfway and cross-fade two of them (a tab that has gone still falls back); the closed island's wings leave in 0.08 s (`compactWingsTransition`) instead of fading under the arriving card; `IslandHoverTests` covers the wait. A swipe on the island (`IslandScrollGesture`, Core, one action per swipe, distances in finger direction) opens, closes or changes track; `close()` leaves `isHoverSuppressed` set until `pointerLeft()`, or hover would reopen it under the resting pointer. Growing and shrinking use different springs (`openingAnimation` / `closingAnimation`), and the expanded page arrives after the shape (`contentArrival`: delayed, blurred, from the top edge; plain fade with Reduce Motion).

- The island does **not** show volume or brightness: macOS's own indicator does, and the user asked for the island's bar (`IslandLevelHUDService`, with its CoreAudio listener and its global monitor for the brightness keys) to be removed. Do not bring it back as a default.
- `FullscreenSpaceProbe` reads the window server's Spaces per display (`CGSCopyManagedDisplaySpaces` in SkyLight, type 4 = full screen); `ZenithIslandWindowController.updateFullscreenVisibility` then sets `isHiddenForFullscreen` (panel alpha 0, hover and swipes off, toasts fall back to the floating panel). `FullscreenWindowProbe` also hides it when the frontmost app has an on-screen window (`CGWindowListCopyWindowInfo`: PID, layer, bounds, alpha; no permission) covering the whole display including the menu-bar strip (games, VLC); a zoomed window starts below the menu bar and does not count. Nothing reports such a window appearing, so it is re-checked on app activation (0, 0.6, 2 s), when a notice is about to show, and when the pointer comes near the island (`recheckCoverNearPointer`, at most twice a second); no timer. Not detected: a covering window drawn transparent; with the menu bar set to hide automatically a zoomed window reaches the top edge and is taken for full screen. The two switches (swipes, hide in full screen) live in `IslandWidgetSettings`.

- `PowerSourceMonitorService` (IOKit run-loop source for power, an `IONotificationPort` on `AppleDeviceManagementHIDEventService` for accessories connecting/leaving, no polling) and `ToastHUDController` produce alerts. When the island is enabled, **all app toasts are routed through the island** instead of the floating toast panel.
- `NowPlayingService` produces `nowPlayingTrack`. Apple Music/Spotify report through `DistributedNotificationCenter` (`com.apple.Music.playerInfo`, `com.spotify.client.PlaybackStateChanged`). Every other app comes from the private `MediaRemote` framework, **which returns nothing (PID 0, nil info) to non-Apple-signed processes on macOS ≥ 15.4** (confirmed on 27.2 while Chrome was playing), so it is not asked in-process: `PerlNowPlayingSource` (Core) starts `/usr/bin/perl`, an Apple-signed binary, which loads `libZenithNowPlayingAdapter.dylib` (the `ZenithNowPlayingAdapter` target; `bundle_app.sh` puts it in `Contents/Frameworks`, a SwiftPM build leaves it beside the executable) with DynaLoader. One perl process stays up while monitoring is on, prints a JSON line per change (title, artist, position, artwork, the playing app), takes `toggle`/`next`/`previous`/`seek <seconds>` on stdin and exits when stdin closes. It also reports which commands the player accepts (`canNext`/`canPrevious`/`canSeek`, from `MRMediaRemoteGetSupportedCommands(queue, callback)`: passing an origin first, as the `...ForOrigin` variant takes, crashes the perl process), which become `NowPlayingTrack.canSkipNext`/`canSkipPrevious`/`canSeek`; a player that does not say keeps its buttons and gets no seeking. The island dims next/previous when the player does not take them, and dragging the progress bar calls `NowPlayingService.seek(to:)` (Music/Spotify over AppleScript `set player position`, anything else through the adapter). **There is no other detection** (the power-assertion probe, the AppleScript tab lookup and the CoreAudio listener were removed): `swift run Zenith` builds only the executable, so run `swift build` first or the adapter is missing and only Music/Spotify show; the same happens if Apple removes perl or closes this door. A browser is shown as the browser (the session has no URL, so YouTube/X are recognised only from the title). `NowPlayingService` takes the feed as `nowPlayingSource` (nil by default, `MockNowPlayingSource` in `NowPlayingAdapterTests`); `ZENITH_E2E_NOW_PLAYING_LIB=$PWD/.build/debug/libZenithNowPlayingAdapter.dylib` runs the real watcher (read-only). The adapter code is Zenith's own; Vorssaint's (GPL) uses the same perl trick and must not be copied. Controls: Music/Spotify are told over AppleScript; anything else goes through the adapter (`MRMediaRemoteSendCommand`, no permission), and gets the hardware media key (`SystemMediaKeys` in `MediaKeys.swift`, needs Accessibility) when the watcher is gone or the system refuses the command. The service is `@MainActor`; `startAdaptiveTicker` only moves the position of a playing track forward (1–2 s). The closed island's artwork tile (`ArtworkThumbnailLayerView`, 22 pt, radius 6, still) and equalizer are Core Animation layers (`EqualizerLayerView` in `NowPlayingIslandViews.swift`), not timer-driven SwiftUI, and artwork is decoded once through `IslandArtwork` (an `NSCache`; the Now Playing card's tint and glow come from `ArtworkPalette`, Core, computed once per cover and kept in the same cache entry: a 16 × 16 reduction, no blur filter, never per tick): that took a playing track from about 17% of a core to about 0.2%, so do not put a timer or a per-tick decode back.

- **Island dock and Tools page**: the open island is "one thing that is going on, and a dock" (the design the user chose over a grid of text buttons, which read as unfriendly). The tabs (`availableTabs`: Now Playing, Widgets, AI, Shelf; tools are **not** a tab) pick what the 80 pt context card (`cardHeight`) shows (the tabs are icon pills in segmented capsules in the strip `tabStripHeight`, which beside a notch is the notch's own row, where each side has ~97 pt: `IslandTabStrip.layout` (Core) puts the first two tabs on the left and the rest and the shelf, a pill with a small count badge, on the right, two 26 pt pills a side, 14 pt in from the edge like the card; without a notch the pills are on the left and the shelf with its count on the right); under it `IslandDock` draws a tray of the pinned tools, a thin rule and All Tools (`IslandToolIcon`, 36 pt, 8 pt apart: seven icons and the rule fit the tray, one more would not, `ZenithIslandGeometry.dockRowWidth(icons:)` against `dockRowRoom`, which `IT-06d` checks, so raising `IslandDockLayout.maxPinned` (6) or the icon size means narrowing something else; in the style `IslandWidgetSettings.dockIconStyle` says: `.tinted`, the default, is a faint tile with the glyph in the tool's colour and a dimmer tile with a grey glyph for a switch that is off; `.color` is the solid-colour tile with a white glyph and a grey one for a switch that is off), with one line above that names the icon under the pointer (`IslandToolStyle.caption`), with one line above that names the icon under the pointer (`IslandToolStyle.caption`), so an unlabelled icon never has to be guessed at. The last icon opens `IslandPage.tools` (`IslandAllToolsPage`): every tool with its **full** name (`IslandTool.title`; abbreviations such as "Area" were the complaint), in `IslandTool.groups`, stacked, four tiles to a row, on a 380 × 430 page (`IslandPage.tools.contentSize`; 38 pt icons in 87 × 72 tiles, the names fit one line); the header beside a notch has ~97 pt a side, so it holds only the back arrow and Close (the title is drawn only without a notch; VoiceOver always has it); Settings and Quit are not in a group but two small circles at the end of that page's dock strip (hidden while editing), so nobody quits Zenith reaching for a tool; "Edit Dock", which sets `IslandDockEditor.isEditing`, is a small capsule in the strip's caption row, and while editing Reset and Done follow the (28 pt, 34 pt a slot) icons: seven slots and both buttons just fit 348 pt, so keep the edit captions short. `IslandToolStyle.activate` decides what a click does: a page (System, All Tools) opens in the island, a switch (`isToggle`: Privacy Shield, Keep Awake) flips in place, anything else closes the island first and calls `ZenithToolActions.run` (App), which the Command Hub's buttons call too; the tools with `opensSettingsWindow` (Settings, Cleaner, Uninstall, Ports, Homebrew) open the Settings window there (see Island pages). The switch is `IslandWidgetSettings.showTools` (default on) → `ZenithIslandState.showsToolsTab` (the name is from when the tools were a tab). While the island can show its dock (`ZenithCommandHubState.launchButtonsAreOnIsland`) the hub leaves out its action grid and its Clean/Boost buttons; `showsActionGrid(query:)` brings the grid back for a search. The hub reads this when it is shown (`refreshLaunchButtonPlacement`) instead of observing the island, whose state changes with every hover.
- **Widgets, Now Playing and AI at 380 pt**: at most two cards side by side. Beside an event the timer card is compact (156 pt max; beside the network speed alone it takes the rest); with the timer, the event and the network speed all on (`IslandWidgetsPanel.foldsNetworkIntoEvent`) the network is not a card but a one-line chip with download and upload (`IslandNetworkChip`) under the event in the event's card, so "Design review" still fits. The Now Playing card shows "Artist · Album" (cut at its end, so the artist stays), a 60 pt cover, 28/32/28 pt controls and a progress bar; the AI tab shows `Today` only per card beside another one (the rest is in the tooltip) and three cards `tight`. Keep Awake's "until turned off" choice is the infinity sign (a tooltip names it): the text did not fit. Check `island-widgets`, `island-now-playing`, `island-ai-agents` and `island-home-keep-awake` in `--render-screenshots` after touching any of them.
- **Keep Awake on the island**: a click on the mug does not call `KeepAwakeService.toggle()` (which means "until turned off" and left the user asking how long it would hold). `IslandToolStyle.activate` stops it if it is on, and otherwise sets `IslandKeepAwakePrompt.isShowing`: the dock, or the Tools page's strip, then shows `KeepAwakeMode.quickChoices` (`IslandKeepAwakeChoices`) in place of its icons. Hovering the mug while it is on shows `KeepAwakeSnapshot.statusText` in the dock's caption. The prompt is dropped when the dock or the page disappears.
- **Arranging the dock**: `IslandDockLayout` (Core, a value with the rules in it: at most `maxPinned` = 6 tools, each once, only tools that have a tile on the Tools page, so never Quit; All Tools is appended by `tools` and cannot be removed) is saved by `IslandWidgetSettings.dockLayout` on every change (`zenith_island_dock_tools`, raw values; nothing is written until the first change, an empty list is a dock emptied on purpose, unknown names are dropped). Three ways to edit, all through that value: the Tools page's Edit mode (`IslandDockEditor.isEditing`; a click on a tile toggles it, a full dock dims what cannot be added), dragging an icon on that page's strip, and the context menu on a dock icon (Move Left / Move Right / Remove from Dock / Edit Dock…), which is also how to reorder without a pointer drag (`accessibilityAction`s mirror it). **The drag is a `DragGesture`, not `onDrag`/`onDrop`**: `ZenithIslandHostingView` overrides the `NSDraggingDestination` methods for the drop shelf without calling `super`, so SwiftUI drops never arrive inside the island, and any pasteboard drag over it turns the shelf's drop target on. `IslandDockLayout.dragTargetIndex` turns a sideways translation into a slot. Two things make the drag smooth, and the first version had neither (the user reported it as jerky): the gesture measures in `.global` coordinates (in the icon's own space the translation changes by a slot each time the icon changes slot, and it flickers between two places), and the dragged icon is not drawn in the row at all while it is held: its slot is left empty and animates with the others, while `IslandDockDragGhost` draws the icon at `IslandDockDragPosition.x`, set without animation on every move (a separate object, so only the ghost redraws at pointer rate).
- **Island pages** (the island is no longer one size): `ZenithIslandGeometry.expandedSize(page:showsDock:)` is 380 × 130 (`expandedWidth` / `expandedHeight`; the card sits at the bottom of that height and the tab strip at the top, so a taller notch only narrows the gap) plus `dockHeight` for the island as it opens, and a page's `contentSize` plus `pageHeaderHeight` for an `IslandPage`. **There are three pages, Tools, System and Displays, and none is wider than the island** (`pageContentSize` clamps to `expandedWidth`). System is `ZenithCommandHubView(inIsland: true)`, 380 × 476, which leaves out what has its own place on the island: the Privacy Shield and Keep Awake tiles, the action grid and Clean/Boost, the Listening Ports button, the Homebrew row, Settings and Quit (the user called each of them out as a duplicate: do not put them back; it keeps the search field, the ring gauges with the network line and Running Apps). Displays is `IslandDisplaysPage` (380 pt, dynamic height per display count), controlling brightness and volume with a link to Display Settings in the Settings window (`SettingsTab.displays`). `IslandPageView` hosts the very views the hub shows, dark because `ZenithIslandPanel.appearance` is `.darkAqua`. **Settings (780 pt), Cleaner (600), Ports (580) and Homebrew (620) are not island pages** (they were, and spread over the menu bar): `ZenithToolActions.run` / `openSettings(on:)` / `openUninstaller()` open Zenith's Settings window (`SettingsWindowController`, `NSApp.activate`, since Zenith is `.accessory`) on the right tab (`SettingsTab.requestSelection`, `HomebrewSettingsLink`, `CleanerSettingsLink` for Uninstall), and `IslandTool.opensSettingsWindow` names those tools; `IslandToolStyle.activate` closes the island first. Do not add a page wider than 380 pt. `ZenithIslandState.openPage` / `closePage` (one step back: to the page this one was opened from, `backPage`, else to the island) / `close`; a switch's extras are in its context menu (`IslandToolMenuItems`: Keep Awake's durations, Privacy Shield's settings, which opens the window), since the System page no longer carries those rows; **a page does not close when the pointer leaves** (`onMouseLeave` returns early), so it has its own ways out: ✕, the back arrow, Escape and a click in another app (`installPageMonitors`: a global mouse-down monitor and a local key monitor that exist only while a page is open). The panel is the size of the island with its dock (`canvasFrame(page: nil)`) and becomes exactly the page's size while one is open: `growCanvas` runs inside the `$page` sink, before SwiftUI draws the page, and the shrink waits 0.45 s for the closing morph, so an idle island costs what it did. Consequences that are easy to break: hit-testing uses `expandedHitRect` / `activeScreenRect`, never the panel's bounds (the canvas is larger than the island); the mouse monitors' fast path uses `pointerInteractionRect`, which is the page's frame while one is open, or a page the pointer left would never wake up again (**carry this over when merging `perf/idle-resource-usage`, which rewrote those monitors as `pollPointer`**); `canBecomeKey` is true only with a page (text fields; the panel is non-activating, so the front app stays in front); swipes are not island gestures over a page; `triggerAlert` does nothing while a page is open and toasts go to the floating panel just under the page (`showsNotices`), because a notice replaces the island's content and would throw the page's state away; a dialog asked for while a page is open (the System page's quit-process confirmation) calls `IslandDialogs.raiseAboveIsland` (the island floats above the menu bar); it sets the level again once the modal session runs, because `runModal()` puts an `NSAlert` or open panel back at the modal-panel level, under the island (the dialog was open but hidden and Zenith looked stuck). A context menu from the open island sets `ZenithIslandState.isShowingContextMenu` (menu-tracking notifications in `ZenithIslandWindowController`) so leaving for the menu does not close the island under it. A page's view is rebuilt whenever the island redraws, so state that must survive lives in a `@StateObject` or a shared model. `--render-screenshots` writes `island-home` (four tabs beside the notch, and the dock), `island-home-idle`, `island-page-tools` and `island-page-system`; `ZENITH_RENDER_NOTCH=1` adds `island-home-notch` / `island-page-tools-notch` / `island-page-system-notch` (a simulated 186 × 32 notch in red: nothing may sit under it) and `-plain` variants without a notch. The Settings window is rendered as `settings-*` (General, Shortcuts, Dynamic Island, Ports, Permissions).

- **No menu bar icon by default**: `AppDelegate.applyMenuBarIcon` creates or removes `MenuBarController`'s status item from `IslandWidgetSettings.needsMenuBarIcon` (the `showMenuBarIcon` switch, default off, **or** the tool dock being off: without either there would be no way to the tools). The Command Hub popover therefore only exists with the icon; its view lives on as the island's System page. Settings is always the window (`SettingsWindowController.show()`; the old `presentationOverride` that sent it to an island page is gone). `applicationShouldHandleReopen` (Zenith opened again while running) shows the Settings window: with no icon that is the way in that always exists, so keep it working.

- **Island widgets**: `FocusTimerService` (counts down to an end date, injected clock, `autoTick: false` in tests) writes `focusTimer`, `CalendarWidgetModel` (an `UpcomingEventProviding`: `EventKitUpcomingEventProvider`, or `MockUpcomingEventProvider` in tests) writes `upcomingEvent`/`calendarAccess`, and `IslandWidgetSettings` writes `showsTimerWidget`/`showsCalendarWidget`. Which expanded tab shows is `ZenithIslandState.resolvedTab(...)`; the closed island shows a running timer beside the notch (`timerIdleWidth`, `compactActivityFrame`, also used for hit-testing). Calendar access is asked only from the Settings switch (`IslandWidgetsCoordinator`); without `NSCalendars*UsageDescription` in Info.plist (`swift run`) the provider reports `.unavailable` instead of asking, because asking would kill the process.

- **Clipboard privacy** (`Sources/ZenithCore/Clipboard/`): `ClipboardCapturePolicy.decide` skips a copy that carries the concealed/transient/auto-generated markers (`SensitivePasteboardMarker`) or that was made while an ignored app was frontmost (`ClipboardPrivacySettings.ignoredAppBundleIdentifiers`, defaults are password managers). `PasteboardMonitor` polls every 0.5 s and reads the frontmost app (`FrontmostApplicationProviding`) at that moment, so a copy followed by a very fast app switch can be attributed to the wrong app. `ClipboardAutoClearController` empties the system pasteboard after 30 s / 1 / 5 / 10 min (default Never) and optionally on lock or sleep (default off), only if it still holds that same copy, never touches the history, and also applies to Zenith's own writes and skipped copies. `ClipboardPasteVariant` (plain text, cleaned link; Shift-Return in `KeyboardNavigationEngine`) never changes the stored item. `TrackingLinkCleaner` strips `utm_*`, `fbclid`, `gclid` etc., `si` only on YouTube/Spotify hosts, `ref_src`/`ref_url` only on twitter.com/x.com; the optional rewrite-on-copy (default off) acts only on exactly one http(s) link and leaves copies with rich text, HTML, files, images or private types alone. Seams: `FrontmostApplicationProviding`, `ClipboardScheduling` (`ManualClipboardScheduler`), `SessionLockEventSource`; `ClipboardStore.shared` is created with `startsPrivacyFeatures: true`, test stores never start them. `ScreenshotRenderer` swaps `ClipboardPrivacySettingsSection.settingsProvider` for made-up settings so a published picture never lists this Mac's ignored apps: keep it that way.
- **Clipboard window** (`ClipboardHistoryView`, `ClipboardCardView`, `ClipboardPanelController`): a wide strip, not a list + preview. The panel asks for 1200 × 372 and `PanelPositioner.dockedFrame` (Core, tested) centres it 32 pt above the bottom of the visible frame of the pointer's screen (narrower and shorter on a small one). It is `NSPanel` (non-activating, key, closes on losing key / Escape, auto-paste unchanged) with a clear background, and the root view is `.glassEffect(.regular, in: 34 pt rounded rect)`; the cards and capsules use `HubSurface` fills, never glass on glass. `show()` rebuilds the root view (`showGeneration`) so the search field takes focus and the row starts at the selected card. Cards are 210 × 236 (`ClipboardCardView`): header (source app icon from `ClipboardItem.sourceBundleID` through `ClipboardSourceAppIcon`, kind, `ClipboardCardContent.relativeTime`, pin), live preview, footer (meta, ⌘1–9 only for the first nine). Everything a card shows is `ClipboardCardContent` (Core), built once per item id in `ClipboardCardContentCache` (counting a big text's characters or lines per redraw is what it avoids); "Code" is `ClipboardItem.looksLikeCode`, a guess on top of `contentKind` (not a new kind, so the Text filter and `contentKind` are unchanged). `sourceBundleID` is read at the poll like the ignored-apps check (same fast-switch caveat), kept through pin/bump/re-copy, and is nil for old or unknown items (the card then draws the kind's symbol). Image thumbnails are decoded once off the main thread by `ClipboardCardThumbnails.service` (its own `ImageThumbnailService`, 440 px, 64 MB, keyed by item id) and read synchronously from the cache when scrolling back. **← and → now move the selection** (as ↑/↓ do) and no longer reach the search field's caret; ⌥, ⌘ and ⇧ with an arrow still do. A click selects, a double-click pastes; the context menu is Paste, plain text, clean link, Open Link, Pin, Delete (the preview pane that held Open and the buttons is gone). `--render-screenshots` draws the strip with `drawsGlass: false` (a flat stand-in over a blob backdrop: glass has nothing to refract in an off-screen window) and made-up items whose apps are system apps, so real icons show; check the glass itself in the running app.
- **Network speed**: `NetworkSpeedMonitor` (Core) reads the 64-bit per-interface counters with `sysctl(NET_RT_IFLIST2)` and counts only `en*`/`pdp_ip*` (a VPN's `utun*` repeats the bytes of `en0`). Speed is computed per interface (`NetworkSpeed.between`), so an interface that appears or resets never makes a spike or a negative. It samples only between `acquire()` and `release()` calls from a visible view (the hub row, the island Widgets card); `pin(_:)` freezes it for `--render-screenshots`.
- **Tracker blocking**: `TrackerBlocklist` (Core, lock-protected, shared with the proxy's connection threads) is checked in `LocalProxyServer` before the DoH lookup in both the CONNECT and plain-HTTP paths; a hit gets `403`. A filtering resolver (`DoHProvider.blocksAdsItself`: AdGuard, a NextDNS profile) is the second layer: an answer of `0.0.0.0` / `::` (`DoHResolver.isBlockingAnswer`) also gets `403` and is counted as blocked, and a name on the never-block list (`TrackerBlocklist.isNeverBlocked`, kept even while blocking is off) is asked of `DoHProvider.neverBlockResolver` instead. The DNS cache is keyed by provider for that reason. The proxy resolves through its injectable `resolver` (tests use a fake). `TrackerBlockingSettings` owns the lists (no built-in list since the filtering resolver took that role; imported file in Application Support + user entries + never-block), is off by default and empties the blocklist while off. `normalize` refuses one-word names and public suffixes, which is what keeps an imported list from blocking everything.

- **Cleaner sizes and removal**: sizes count everything a deletion removes (hidden folders such as pnpm's `node_modules/.pnpm`, and the inside of `.app`/`.framework`/`.dSYM`, which DerivedData is mostly made of), so never pass `.skipsHiddenFiles` or `.skipsPackageDescendants` to an enumerator that sizes or checks activity. `SystemCleanerService.removeItemMakingWritable` makes the folders *inside* an item writable and retries (Go's module cache is read-only on purpose); `lastFailedItemNames` reports what stayed behind. A project's "untouched N days" is the newer of its build folder and the project's own files (`ProjectPurgeService.lastActivity`), not the build folder alone.
- **Privacy Shield limits and input**: an app started from Finder has 256 open files, and a tunnel uses two, so `LocalProxyServer` raises the limit (`FileDescriptorLimit`, 10 240). The port the user types goes through `PrivacyShieldStatistics.validPort` (a bare `UInt16(port)` traps on 70000), and a typed DoH resolver goes through `DoHProvider.custom(urlString:bootstrapIP:)` / `nextDNS(profileID:)` and is applied when editing ends, not on every key.

- **If the app dies with the shield on**: `ProxyWatchdog` (started by the real `SystemProxyManager` when it enables the proxy, stopped when it restores) is a `/bin/sh` child that outlives the app, waits for its PID, and then switches the proxy off only if it still points at Zenith's port and nothing listens there; the next launch still restores the user's settings. Do not rely on an unmount notification or a view's `onDisappear` for this: `willUnmount` also arrives for an eject that fails, and the process dies with SIGBUS (exit 138) right after a forced one. `AppLocation.isOnMountedVolume` drives the warning when the shield is turned on from a disk image or external drive.
- **Scheduled cleaner scan**: `CleanerScanScheduler` (Core) and `ScheduledCleanerScanController` (App, started from `AppDelegate`) are off by default and run a daily, weekly (default) or 30-day scan only while the app runs, on their own `SystemCleanerService` at low priority. **Nothing on the scheduled path may call a deleting function**; `SCH-15` proves a scan leaves a temporary home byte-for-byte unchanged. It notifies once (island notice, or the floating toast when the island is off or hidden) when at least `CleanerScanScheduler.noticeThresholdBytes` (1 GB) can be cleaned, and again only after the amount grows by another 1 GB. That constant also appears as literal text ("1 GB") in the Settings → Cleaner footer, so change both.
- **Updater** (`Sources/ZenithCore/Updates/`, Core; `UpdateController` + `UpdatesSettingsSection` in the app): `ZenithUpdater` checks `releases/latest` once a day while running (on by default, `UpdateSettings`; `UpdateCheckSchedule` is the pure due/notify decision, one notice per version) and installs only after the user's click and confirmation. Trust is the signature, nothing else: the downloaded app must satisfy the **running app's designated requirement** (`SecurityFrameworkSignatureVerifier`, Security framework, all architectures + nested code + strict + no escaping symlinks), so **every release must be signed with the same certificate** as the one before (the "Zenith Local Signing" identity from `setup_signing.sh` is now the update authority; keep a `.p12` backup; if it is lost, users install the next release by hand once). An ad-hoc copy (cdhash-only requirement), a translocated one, one on `/Volumes` or a read-only volume, or an unwritable location gets "Download…" (DMG to Downloads with quarantine set, opened in Finder) instead. `UpdateInstaller` order: re-check the release (exact `github.com/mynameisbat/zenith-macos/releases/download/<tag>/Zenith-<v>.dmg`, size cap 300 MB), download to a 0700 temp folder (redirects only to `*.githubusercontent.com`), exact size + SHA-256 when GitHub publishes one, `hdiutil attach -nobrowse -readonly -noautoopen -mountpoint <temp>` (detach always, `-force` fallback), copy Zenith.app into a hidden staging folder beside the installed app, verify THAT copy (identifier, announced version == bundle version > running, signature), `replaceItemAt` swap, old app to the Trash. It never removes quarantine and never relaunches by itself: `RelaunchHelper` (a `/bin/sh` child like `ProxyWatchdog`, PID and path as arguments, gives up after 60 s) reopens the app after `NSApp.terminate`, which restores the system proxy as any quit does; Privacy Shield is not turned back on. `create_dmg.sh` refuses an ad-hoc `Zenith.app` (`ZENITH_ALLOW_ADHOC_DMG=1` for a local test only). **Minimum macOS** (every release that raises `LSMinimumSystemVersion`, today 26.0): a release states what it needs in ONE line of its GitHub release notes, `Minimum macOS: 26.0` (`MinimumSystemMarker`, Core: any case and spacing, Markdown emphasis or a list/quote marker around it, 1–3 numbers, first valid line wins; the format is documented on that type). `create_dmg.sh` reads the value from the built app's own `LSMinimumSystemVersion` (and refuses an app without one) and prints the exact line to paste at the end of its output, so **paste it into every release's notes**; installed copies cannot be changed afterwards, so a release published without it is offered to Macs that cannot run it (only the install-time check then stops it, after the download). `UpdateReleaseParser` puts it in `UpdateRelease.minimumSystemVersion` (a body of the wrong type states nothing and never fails the release). `ZenithUpdater.performCheck`: a newer release whose minimum is above `systemVersion` (injected, default `AppVersion.runningOperatingSystem`) is **not** `availableRelease`: `phase = .requiresNewerSystem`, `unsupportedRelease` is set, there is no island notice, `lastNotifiedVersion` is untouched, `install`/`downloadForManualInstall` do nothing, and Settings → General → Updates shows "Zenith 3.0 needs macOS 26 or later. This Mac runs macOS 15.6." with only What's New (the release page). A release that states nothing counts as compatible. Second, authoritative check in `UpdateInstaller`: `checkReleaseAgain` refuses a release whose notes state a newer macOS before anything is downloaded (manual download too), and after staging `UpdateInstallPolicy.candidateRejection` compares the staged app's `LSMinimumSystemVersion` with the Mac (`.needsNewerSystem`; a key that is present but not a version is `.unreadableInfo`), so nothing is replaced. Tests use fake bundles in temp folders, a fake `hdiutil` and an injected verifier; `ZENITH_E2E_SIGNING=1` (`UpdateSignatureE2ETests`) signs fake apps with two identities in a throwaway keychain and runs the real verifier. `ScreenshotRenderer` swaps `UpdatesSettingsSection.updaterProvider` for made-up state: keep it that way.
- **Deletion gate**: `isPathSafeForDeletion` allows only entries inside `containerRoots` (Library/Caches, DerivedData, Logs, …) and exactly the cache folders in `itemRoots`; a new scan target needs an entry there, and `AUD-10` fails if a scan offers something the gate refuses. Project purge treats `Pods` like `build`/`dist`: offered only when Git ignores it.

### Localization (English, Vietnamese, zh-Hans, ja, ko, fr, de, es)

- The English text in the code is the key. `Localization/<lang>.lproj/` (`Localizable.strings`, `InfoPlist.strings` for the permission prompts) is copied into `Zenith.app/Contents/Resources` by `bundle_app.sh`, whose Info.plist lists `CFBundleLocalizations`. `swift run` has no bundle, so it is always English; to see Vietnamese, bundle and run `Zenith.app/Contents/MacOS/Zenith --render-screenshots DIR -AppleLanguages '(vi)'`.
- A literal passed to `Text`, `Button`, `.help`, `.accessibilityLabel` … is looked up; **`Text(someString)` is not**. Shared components take `LocalizedStringKey` (or a `Text` / `verbatim:` init for data). Strings built in code and every user-facing string in Core use `String(localized:)`. `ToastHUDController.show(message:)` and `DestructiveConfirmation.confirm(title:message:destructiveTitle:)` take `String.LocalizationValue`; `show(verbatim:)` / `confirm(verbatimTitle:…)` are for text that is already localized (errors, Core's strings).
- Write whole sentences per case (`count == 1 ? "1 item" : "\(n) items"`), never "\(n) \(noun)". Interpolate `String(n)` for numbers that must not get digit grouping (ports, PIDs, pixel sizes), or Vietnamese shows "8.080". Strings compared with what another app reports (Music's `"Playing"` state) must stay unlocalized.
- After adding UI text, run `scripts/check_localization.sh [lang]` (default `vi`; keys come from the compiler's `-emit-localized-strings`, as Xcode's String Catalogs do) and add the translation to every `Localization/*.lproj` (Vietnamese is written by hand; the other six were machine-assisted and follow the same keys, order and comments as `vi.lproj`). `LocalizationTableTests` checks that every translation parses and keeps its key's `%@`/`%lld` arguments.
- VoiceOver: icon-only buttons carry `.accessibilityLabel`, tappable views that are not buttons get `.isButton` and actions, and `ZenithIslandState.triggerAlert` / toasts are read aloud through `AccessibilityAnnouncer`.

### Things that touch the real system

- **Privacy Shield**: `LocalProxyServer` listens on `127.0.0.1:8080` (the `NWListener` has `requiredLocalEndpoint` 127.0.0.1: an interface restriction alone left it on `*:port`, which `LP-14b` checks with lsof; the non-loopback rejection stays as a second layer) and `SystemProxyManager` points the macOS system proxy at it with `/usr/sbin/networksetup`, after saving the user's previous proxy and bypass settings (also persisted in `UserDefaults`). Disable restores them, and only for settings that still point at Zenith. A run that was killed is repaired on the next launch (`recoverFromUncleanShutdown`, called from `AppDelegate`). The proxy is switched on only after `startAndAwaitReady` confirms the port is bound. Turning the shield off from the UI calls `LocalProxyServer.stop(gracePeriod: 30)` (`PrivacyShieldController.stop()`, only when the proxy settings were restored): the listener is cancelled so nothing new arrives, connections already open keep relaying and `closeDrained` cuts what is left after 30 s; `stop()` still closes everything at once. Quitting with the shield on ends every connection through it (they live in Zenith's process). Known gap: the listener's `.cancelled` handler sets `_isRunning = false` without checking that it belongs to the current listener, so a very quick stop-then-start can mark the new listener as not running. Upstream connections are one-request-per-connection for plain HTTP (`Connection: close`); don't let a `.failed` upstream state cancel a tunnel that is already piping, or in-flight response bytes are lost.
- **Cleaner/purge services** (`SystemCleanerService`, `ProjectPurgeService`, `AppUninstallerService`, …) really delete files (`trashItem` / `removeItem`). Don't point them at real home-directory paths when experimenting.
  - `SystemCleanerService(homeDirectory:)` scans and cleans only that home (tests use a throwaway one). It must never offer Docker Desktop's `Library/Containers/com.docker.docker/…` (the VM disk holds every image, container and volume; `isPathSafeForDeletion` refuses it), and the Trash category is listed but unselected. "Application Caches" skips `com.apple.*` (except Xcode's) and offline-media/sync apps (`isDataBearingCache`), partial downloads are only offered after a day untouched, and `selectionSummary` names the largest items so the confirmation shows what is really going. Both the Settings tab and the Command Hub's "Clean" badge confirm via `DestructiveConfirmation` and list what goes (`selectionSummary`); keep it that way.
  - `ProjectPurgeService` offers a folder only if the project type rebuilds it (`PurgeArtifactType.projectMarkers`), and `bin`/`obj`/`build`/`dist` also need `git check-ignore` to say it is ignored. `ExternalDriveSanitizerService` only works on a mounted external volume's root and treats a `._*` file as junk only if it starts with the AppleDouble magic.
  - Foundation hides `._*` files from `FileManager.enumerator`, `contentsOfDirectory` and friends; only POSIX `readdir` (or `subpathsOfDirectory`) lists them.
  - `OrphanedAppLeftoversService` offers only entries named like a bundle identifier (never `Google`, `JetBrains`, `com.docker.*`, `com.apple.*`), skips an app Launch Services or a running process still knows and any app from the same vendor as an installed one, and anything touched in the last 30 days; `purge` re-checks all of it. `InstallerPurgeService` scans Downloads and Desktop only (not `/tmp`), treats a `.zip` as an installer only if it is named like one, finds mounted images by `hdiutil info` path, and `purge` skips a file that changed since the scan. `URL` caches resource values: re-check a file through a fresh `URL(fileURLWithPath:)`.
  - `ProjectPurgeService`, `InstallerPurgeService`, `OrphanedAppLeftoversService` and `ExternalDriveSanitizerService` are reached from Settings → Cleaner through `CleanupToolModel` (Core, tested): scan, tick, `cleanSelected(confirm:)`, which asks first and removes nothing when declined. Leftovers start unticked. Projects, installers and leftovers go to the Trash; drive junk is deleted (the dialog says so). Add a tool by writing a factory there, not by calling a service from a view. Views here use `@StateObject`/`@ObservedObject` only: the SwiftUI macro plugin (`@State`) is missing from a Command Line Tools build.
  - **Uninstaller** (Settings → Cleaner → Uninstall): `AppUninstallerModel` (Core) lists apps without measuring them (`AppUninstallerService.listInstalledApps`, `/Applications` and `~/Applications`, one folder level down) and opens the picked one as `CleanupToolModel.uninstaller(app:)`: the app is the first row, leftovers tied to it only by display name (`AppLeftoverItem.matchedByName`) start unticked. `AppUninstallerService.uninstall` asks an open app to quit and gives up with nothing removed if it stays open (`quitTimeout`), moves the app first (a refusal stops everything), then only leftovers a fresh lookup still ties to the app. Names from an Info.plist are untrusted: an identifier must pass `isUsableBundleIdentifier` and match whole dot-separated components (`entryName(_:startsWithIdentifier:)`), so `com.acme.app` never claims `com.acme.apple.plist`. Seams: `homeDirectory`, `applicationDirectories`, `TrashMover`, `SystemCommandRunner` (launchctl), `RunningAppControl`, `recordHistory`; `AppUninstallerFlowTests` uses a sandbox with its own "Trash". The island's Deep Uninstall uses the same `uninstall` with every leftover.
- `BinarySlimmerService` never edits an installed app in place: it thins and re-signs a clone, runs `codesign --verify`, swaps it in atomically and sends the original to the Trash. The island's "Deep Uninstall" and "Slim" actions go through `IslandAppActionCoordinator`, which asks for confirmation first.
- Screen capture needs Screen Recording permission; Accessibility is used by `AutoPasteService` and as the fallback for the hardware media keys (`MediaKeys.swift`); AppleScript control of Music/Spotify, Music artwork and asking Finder to trash protected leftovers need Automation. The Settings → Permissions page (`ZenithPermissionsModel`, `PermissionsGuideView`) reads each state without prompting and never requests anything; Automation is `askedPerApp` because macOS reports it per target app. A feature that gains an on/off switch must be mapped in `LiveFeatureActivity` (today only the calendar widget is), or the page keeps calling it always available and cannot warn about a permission nothing uses.
